# 产品需求规格

状态：已整理；MVP 子集已于 2026-09-04 实现并验收
范围：通用核心、项目策略、Codex Skill 入口及可替换适配器

## 1. 规范说明

本文只记录已确认的产品行为。`必须` 表示强制要求，`应` 表示有明确偏好的要求，`可以` 表示允许但不承诺进入 MVP。具体 MVP 取舍见 [mvp.md](mvp.md)，暂定技术和未决问题见 [architecture-decisions.md](architecture-decisions.md)。

验收时，日志、数据库记录、Git 差异、命令输出、测试结果或人工可核查的界面反馈均可作为证据；只由模型声明“已完成”不构成证据。

## 2. 产品与边界

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| PROD-01 | 系统必须提供风险感知的多模型任务路由、执行、验证、审核、升级和恢复能力，而不是绑定固定模型的调度脚本。 | 替换模型或供应商后，任务合同、状态、门禁和运行记录仍适用。 |
| PROD-02 | 通用核心必须固定任务合同、风险与权限规则、模型选择方法、执行状态机、审核门禁、失败升级、费用与隐私控制及运行记录。 | 这些能力不依赖项目专属提示词或某个模型。 |
| PROD-03 | 具体模型、供应商、Agent Engine、本地模型服务以及顶层规划或审核模型必须可替换。 | 注册或替换适配器不要求修改领域无关的核心规则。 |
| PROD-04 | 系统必须采用“通用核心 + 项目级配置”。 | 不同项目可分别定义领域风险、验收标准、隐私数据和模型偏好。 |
| PROD-05 | 股票投研应作为首个真实试验项目，但金融规则不得写死进通用核心。 | 删除试验项目配置后，核心中不存在金融专属判断。 |
| PROD-06 | 系统必须可完全停用；停用后用户仍能通过 OpenCode 等方式人工继续，且 Git 历史和已有产物可用。 | 无控制平面进程时，项目文件、分支、差异和记录仍可读取与接管。 |

## 3. 平台与入口

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| PLAT-01 | 协作内核必须平台无关，并通过适配器连接 Codex Skill、OpenCode、LM Studio、DeepSeek API 及未来入口或供应商。 | 核心任务格式和状态语义中没有供应商专属必填字段。 |
| PLAT-02 | Codex Skill 必须是第一版用户入口之一，并与 Terminal 共用同一套计划、状态和授权。 | 同一运行在 Skill 和 Terminal 中显示相同标识与状态。 |
| PLAT-03 | 第一版在 macOS 开发和验证；核心任务格式、SQLite 数据及适配器接口应保持跨平台。 | 核心持久化不依赖 macOS 专属路径或 API；专属增强被隔离。 |
| PLAT-04 | 第一版不开发网页控制台。 | MVP 交付清单中没有 Web UI。 |
| PLAT-05 | AgentFlow 必须能通过 OpenCode 调用计划与授权快照共同限定的远程 provider/model，第一版远程能力只能执行独立、只读的 `review`/`rereview`，不得绕过控制平面或承担实施与修改。 | 使用 OpenCode 替身可观察到参数数组 `run --model <provider>/<model-id>`；未授权 provider、写入角色或非只读请求在进程启动前被确定性拒绝。 |

当前环境中的 Qwen 3.8 27B Q4、Qwen 3.8 27B 8-bit、GPT-OSS、DeepSeek V4 Flash 和 DeepSeek V4 Pro，以及未来可能采用的 GPT、Claude 或其他模型，均只视为用户提供的候选记录；名称、可用性和能力须在使用时发现或验证，不能成为通用 Skill 的永久默认值。

## 4. 模型发现、选择与信任

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| MODEL-01 | 用户必须能指定具体模型、各角色模型、选择策略、白名单、黑名单、托管模式可自动调用的模型及必须逐次确认的模型。 | 计划可表达上述选择，路由结果不能越过限制。 |
| MODEL-02 | 选择策略至少必须表达本地优先、成本优先、均衡和质量优先。 | 相同候选集在不同策略下产生有理由的排序。 |
| MODEL-03 | 用户未指定模型时，系统必须发现已安装、已加载、可调用且已验证的本地模型，以及已配置的远程供应商。 | 推荐结果标明发现来源和实际可用状态。 |
| MODEL-04 | 必要时可以查询官方资料了解当前主流模型，并按任务、风险、成本、速度、隐私、工具能力、用户信任和历史表现推荐。 | 推荐记录含决策依据，并区分事实、估计和历史测量。 |
| MODEL-05 | 推荐必须区分“当前可立即调用”和“值得考虑但尚未接入”。 | 未接入模型不会被路由为可执行模型。 |
| MODEL-06 | Skill 对未接入模型只能给出建议，不得自动下载模型、安装环境、注册账号、购买额度、申请或保存密钥、修改供应商配置。 | 推荐流程结束后，环境和外部账户无上述变更。 |
| MODEL-07 | 模型注册表至少记录供应商、模型 ID、版本或快照、本地/远程、可用性、上下文长度、工具能力、成本、速度、用户信任等级、项目实测、历史成功率、平均返工次数和最高允许风险等级。 | 任一可路由模型均有完整或显式未知的字段。 |
| MODEL-08 | 信任等级至少支持 `unverified`、`probationary`、`trusted`、`restricted`。新模型或新版本不得自动继承旧版本信任。 | 新版本首次登记时信任状态独立，且有变更记录。 |
| MODEL-09 | 每次任务必须记录模型及版本、任务类型与风险、测试结果、一次通过率、审核发现的 P0/P1、返工次数、耗时、费用和最终批准状态。 | 可按一次任务追溯全部字段。 |
| MODEL-10 | 原始任务和敏感内容必须留在所属项目；跨项目通用统计只能使用本地保存的脱敏指标。信任等级提升必须由用户决定。 | 全局库不含原文；自动运行不能自行提升信任等级。 |
| MODEL-11 | 在项目实测前，DeepSeek V4 Pro 可以参与重要任务和关键架构的反方审核，但不得自动成为最高风险架构任务的唯一规划者。 | 未满足实测条件的计划会阻止该唯一规划者组合。 |
| MODEL-12 | 信任统计必须按供应商、精确模型版本和任务类型隔离；至少有 20 个经独立审核的任务后，系统才可以提示提升信任，且不得自动提升。 | 小于 20 个合格样本时无升级建议；满足样本量后仍需用户确认。 |
| MODEL-13 | 模型发现必须区分 `unsupported`、`not_configured`、`discoverable`、`unavailable`、`callable_unverified` 与 `callable_verified`；OpenCode 无推理列表只能证明配置/可发现，不能证明真实可调用。 | 发现流程不发送推理请求；只有另行计划、哈希批准的 smoke test 才能写入 `callable_verified`。 |

## 5. 激活、运行模式与授权

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| AUTH-01 | Skill 可以被自动建议，但识别到复杂任务不得自动启动模型；进入多模型调度前至少需要一次明确激活。 | 无激活记录时不会产生模型调用。 |
| AUTH-02 | 系统必须支持托管、监督和自适应三种模式。托管模式按一次批准的完整计划运行；监督模式在每次实施、审核或复审模型启动前确认；自适应模式只让普通节点自动运行，关键模型和关键节点逐次确认。 | 三种模式对同一计划产生符合定义的确认点。 |
| AUTH-03 | 自适应模式应作为推荐选项，但未经用户选择不得自动启用。 | 新计划显示推荐但保持未选或用户既有明确默认。 |
| AUTH-04 | 授权必须绑定执行计划版本和内容哈希，并记录任务、模型、文件、预算、隐私策略、运行模式、最大重试、停止/升级条件和有效期。 | 任一可执行计划均能查到完整授权快照和匹配哈希。 |
| AUTH-05 | 新增任务、扩大文件范围、改用未授权模型、提高预算、扩大远程数据范围或增加外部副作用/权限时，原授权必须失效或要求增量授权。 | 修改后启动被阻止，并明确显示需重新授权的差异。 |
| AUTH-06 | 用户暂时不在线时，系统只能在现有有效授权内先行判断并继续；需要新权限、超预算、发送未授权敏感数据或执行高影响操作时必须暂停。 | 离线场景既不会无故等待授权内工作，也不会越权。 |
| AUTH-07 | 计划必须使用带 schema 版本、稳定键排序且排除易变运行字段的规范化 JSON，并以 SHA-256 生成授权哈希。增量授权必须生成新的完整授权快照；授权在计划变化、运行结束或 24 小时后失效，以最先发生者为准。 | 相同有效计划得到相同哈希；任一授权范围变化都产生新哈希且旧授权不可继续使用。 |
| AUTH-08 | MVP 中托管、监督和自适应三种模式都必须形成端到端闭环；自适应模式只能按明确风险阈值与关键节点标记设置确认点，不得使用学习型路由或隐式改变策略。 | 三种模式均可完成同一计划，且自适应模式的每个确认/放行决定可以由静态规则复现。 |
| AUTH-09 | 计划与授权快照必须同时绑定 provider、精确模型键、角色、文件、禁止动作、预算、远程数据权限、隐私策略、运行模式和有效期；任一范围变化必须重新执行 plan show、哈希批准、authorize、start 顺序。 | provider 或远程 Reviewer 权限变化后旧授权不能启动调用；OpenCode 已配置模型不能替代计划授权。 |

## 6. 风险与安全

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| RISK-01 | 风险必须分为业务重要度与操作安全等级两个维度。 | 任务卡和运行记录分别保存两个值。 |
| RISK-02 | 业务重要度由用户最终决定；Agent 必须先行评估并给出建议。用户与建议不一致时必须保留用户值及分歧理由。 | 风险记录可同时展示用户决定、建议和理由。 |
| RISK-03 | 操作安全等级必须由系统依据数据、权限和行为判定；降低业务重要度不能取消硬性安全边界。 | 高安全风险操作仍触发门禁。 |
| RISK-04 | 执行中风险升级若仍处于授权模型、预算和权限内，系统必须加强模型、测试或审核并继续；否则必须暂停并请求授权。 | 两类风险升级分别产生继续或暂停记录。 |
| RISK-05 | 业务重要度必须使用 `B0` 琐碎、`B1` 普通、`B2` 重要、`B3` 关键；操作安全必须使用 `S0` 本地只读且无敏感数据、`S1` 可逆本地修改或授权 D0 远程调用、`S2` D1/D2 远程处理或有边界外部写入、`S3` 高影响或不可逆操作。两个维度不得合成单一总分。 | 每个任务分别保存两个枚举；高 S 等级不会被低 B 等级抵消。 |

## 7. 费用控制

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| COST-01 | 系统必须支持本地免费、固定预算和效率优先三种费用模式。 | 本地免费模式阻止收费 API；固定预算不超额；效率优先仍受保护规则约束。 |
| COST-02 | 效率优先不得解释为无限重试、同工重复调用、简单任务滥用昂贵模型、通过后追加无意义审核或免除费用记录。 | 对应行为被拒绝、去重或熔断。 |
| COST-03 | 费用控制必须记录单次调用、计划预算和应急预留，并支持最大重试、重复调用检测、异常费用提醒、费用熔断及预算耗尽后的本地降级。 | 可重放一个预算耗尽场景并检查各项证据。 |
| COST-04 | 预算用尽后应默认回退本地模型；若关键质量门槛无法满足，只能标记为等待更强审核，不得标为通过。 | 降级后状态与审核结论准确反映未满足门槛。 |
| COST-05 | 收费调用发出后结果未知时，必须先按供应商请求 ID 或幂等键查询；无法确认则标记为 `UNKNOWN` 并暂停人工处理，不得自动重试。预算预留不构成重复扣费授权。 | 模拟网络中断后不会产生第二次收费请求，且状态和人工处理原因可追溯。 |
| COST-06 | 本地调用实际费用必须记录为零；远程调用必须记录 OpenCode 报告的实际费用。provider 未报告费用时必须记录 `cost_unavailable` 而非伪造零，并保留 Token、状态及 provider/model 汇总。 | 费用命令分别展示已确认远程费用、费用未知调用数和 provider/model 汇总；缺失费用的远程替身不会生成零金额费用记录。 |

## 8. 数据隐私

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| PRIV-01 | 数据分类至少支持 D0 公开、D1 项目内部、D2 敏感内部和 D3 严格隐私。 | 进入模型上下文的数据均有分类或被默认按更严格等级处理。 |
| PRIV-02 | D0 可以自动发送远程模型；D1 需项目级授权且只发送最小必要片段；D2 默认本地，只有本次计划明确授权并通过自动脱敏检查时才能远程发送；D3 禁止发送远程模型。 | 各等级的发送测试符合策略；D2 缺少任一条件时被阻止。 |
| PRIV-03 | D3 至少包括个人持仓、持仓成本、可用资金、主要持仓、个人身份信息、密码、API Token 和密钥。 | 含这些数据的远程请求被阻止。 |
| PRIV-04 | 源代码只有在项目级授权并自动脱敏后，才可以向远程模型发送最小必要差异。未发布研究结论默认保留本地。 | 远程负载不含完整仓库或未授权研究结论。 |
| PRIV-05 | 远程发送前必须检查密钥、Token、账户字段、个人路径和可组合推断的隐私信息，并记录接收模型和发送材料范围。 | 检测命中会阻止或脱敏；发送审计可追溯。 |
| PRIV-06 | 密钥只允许通过环境变量或本机密钥管理器提供，不得进入仓库、运行日志或模型上下文。 | 仓库与持久化记录扫描无密钥明文。 |
| PRIV-07 | 远程 Reviewer 只能接收最小 Review Packet：任务标识与目标、风险、验收条件、禁止动作、相关实际差异、必要测试/证据和明确审核问题。发送前必须扫描敏感字段并记录 packet SHA-256、大小、task/call、provider/model 与隐私策略版本，不得在日志复制正文。 | 替身捕获的 prompt 不含完整仓库、历史对话、数据库、无关日志或个人路径；审计记录可验证 packet 哈希和大小。 |

## 9. 任务合同与路由

每个任务必须拆成有限数量且可独立验收的工作单元，不得为了并行或形式过度拆分。任务卡至少包含以下字段；字段语义或枚举的精确定义仍可在实现设计时补充，但不得删除：

```yaml
task_id:
objective:
risk_level:
allowed_files:
forbidden_actions:
acceptance_criteria:
data_sensitivity:
implementation_model:
review_model:
fallback_model:
max_remote_cost:
max_retry_count:
escalation_conditions:
expected_outputs:
implementation_max_steps:
implementation_timeout_seconds:
implementation_max_continuations:
```

其中 `risk_level` 是包含 `business_importance` 与 `operational_safety` 的对象，分别使用 AD-25 确定的 B0-B3 与 S0-S3 枚举。

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| TASK-01 | 确定性程序应负责日期、计算、格式、风险分数和可自动判定的测试。 | 可确定结果不需要模型自由判断。 |
| TASK-02 | 本地或便宜模型应优先处理批量、机械、边界明确工作；中等模型处理普通实现和审核；强模型保留给关键规划、复杂故障、冲突裁决和最终 P0 审核。 | 路由理由符合任务属性；强模型不会默认承担全部实现。 |
| TASK-03 | 实施模型、审核模型、后备模型及费用、重试、升级边界必须在执行前进入任务合同。 | 缺失必填字段的任务不能进入执行状态。 |
| TASK-04 | 本地实施任务必须携带有限正整数步骤预算字段 `implementation_max_steps`，进入任务合同与计划哈希；旧计划未提供时默认 8，允许范围为 1–32。修改该字段必须改变计划哈希并使旧授权失效。 | 复杂本地任务显式配置 12–16 等预算；越界、非整数或负值在构造/解析时被拒绝；改变预算后旧授权不能授权修改后的计划。 |
| TASK-05 | 本地实施任务必须携带整数超时字段 `implementation_timeout_seconds`，进入任务合同与规范化 JSON/计划哈希；旧计划未提供时默认 900，允许范围为 60–14400。布尔、字符串、浮点数、0、负数及越界值在构造或解析时被拒绝。修改该字段必须改变计划哈希并使旧授权失效。 | 复杂本地任务显式配置更长超时；`plan show` 展示该字段；越界或错误类型被拒绝；改变超时后旧授权不能授权修改后的计划。 |
| TASK-06 | 本地实施任务必须携带非负整数续接预算字段 `implementation_max_continuations`，进入任务合同、规范化 JSON 与计划哈希；旧计划未提供时默认 0，允许范围为 0–8，0 表示步骤耗尽后不续接。布尔、字符串、非整型浮点、负数及越界值在构造或解析时被拒绝。修改该字段必须改变计划哈希并使旧授权失效。 | 复杂本地任务可显式配置续接次数；`plan show` 展示该字段；越界或错误类型被拒绝；改变续接预算后旧授权不能授权修改后的计划。 |

## 10. 质量门禁

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| QA-01 | 同一模型不得完成“实施、自测、审核、宣布完成”的全部流程。 | 审核记录来自独立上下文；不能由单次实施调用自批。 |
| QA-02 | 标准流程必须覆盖实施、自测、确定性测试、独立审核、修复、原审核方复审，并在阻断问题清零后批准。 | 运行时间线包含所需节点，存在阻断问题时不能批准。 |
| QA-03 | 审核必须使用全新上下文且默认只读。普通任务可以使用同一模型家族，但不得向审核上下文提供实施方解释；重要或关键任务必须使用不同模型家族。 | 审核调用无写权限；关键任务缺少跨家族审核时停在等待更强审核。 |
| QA-04 | 重要任务的验收标准必须在实施前确定，并由独立模型补充失败路径和边界测试；测试不能完全由实施模型设计。 | 测试设计的时间戳与来源符合要求。 |
| QA-05 | 审核输入应优先包括原始需求、验收标准、代码差异、测试和原始证据，避免用实施模型的长篇说明锚定审核者。 | 审核上下文清单可检查。 |
| QA-06 | P0 必须覆盖越权、隐私泄露、数据破坏、重复收费和关键结论错误；P1 必须覆盖未满足验收标准、明显回归和恢复失败。P0/P1 均阻断批准，P2/P3 为非阻断改进。 | 任一未关闭 P0/P1 都使批准失败；P2/P3 保留在审核记录中。 |
| QA-07 | 远程 Reviewer 必须强制只读并禁用编辑、写入、Shell、外部目录、网页工具、任务/子 Agent、Skill 和交互升级；输出必须解析为含 `approved` 与结构化 findings（severity、title、explanation 及适用的 path/remediation）的结果。 | 权限配置和解析测试覆盖全部禁止能力；未解决 P0/P1 或无法确认的输出均不能批准。 |
| QA-08 | 模型调用的步骤上限耗尽或其他已知输出不完整终止必须记为带类型原因的已知失败，不得记为 `completed`、`UNKNOWN` 或有效实施/审核结果。必须保留已确认 Token、耗时和费用，在下一质量节点前安全暂停，且不得自动重试。 | 无论退出码为 0 还是正数非零退出，只要 stdout 事件/最终文本显示严格步骤耗尽，实施不进入自测/审核，Reviewer 不生成 review 记录；暂停原因和调用证据可审计，resume 不会重复调用。由 signal 终止或结果不可确认的调用仍保持 `UNKNOWN`，不得仅凭不完整文本改为已知失败。 |
| QA-10 | 本地实施调用超过 `implementation_timeout_seconds` 时必须终止进程组并记为 `UNKNOWN`，不得自动进入自测、审核、重试或完成；必须保留部分 stdout 中已确认的 Token、耗时、OpenCode 会话 ID 及结构化审计元数据，同时诚实记录 `usage_unavailable` 与 `token_source`。部分输出不得当作可信 `output_text`；原始元数据只保存最小必要字段，并以 SHA-256 记录部分 stdout 哈希。 | 模拟超时后调用终态为 `UNKNOWN`，暂停原因为 `unknown_model_call`，resume 被阻止；数据库保存 Token/耗时/会话 ID/`termination_reason=timeout`/`token_source`；无可用 Token 时 `usage_unavailable=true` 且不伪造零费用；`output_text` 为空；重复或重叠的部分输出不会重复累计 Token。 |
| QA-11 | 本地实施/修订角色调用因步骤上限耗尽而已知失败时，仅当全部条件满足（本地模型、实施/修订角色、同一模型与 worktree/文件范围、`implementation_max_continuations` 限额内、文件范围核验通过、无暂停/取消/接管、非 `UNKNOWN`/超时/signal/费用未知）才可在同一 OpenCode 会话内以新 segment 续接；每个 segment 拥有唯一 call_id、request_key、segment_index 与 continuation_of_call_id，并单独记录 Token、耗时与费用；续接决定必须持久化为 `continuation.scheduled` 事件，segment 间进程重启后 resume 必须只续接一次且不重复已完成 segment。任一条件不满足时必须保持安全暂停且不得续接或重试。 | 步骤耗尽后实施在限额内以 `--session` 复用同一 OpenCode 会话继续并最终完成；远程 Reviewer、`UNKNOWN`、超时、signal、越界文件、缺失会话 ID 或超过限额的场景保持暂停且 resume 不产生重复调用；续接 segment 的调用记录与 `continuation.scheduled` 事件可审计。 |
| QA-09 | Reviewer 提示必须在 Review Packet 之外强制 JSON-only 协议：只允许一个顶层对象，`approved` 必须是 boolean，`findings` 必须是数组，每项必须有 P0-P3 `severity`、字符串 `title` 和 `explanation`，可选字符串 `path`/`remediation`。Markdown fence、前后散文、缺字段、错类型或非法严重度均不得猜测性解析；任一 P0/P1 必须覆盖 `approved=true`。 | 有效纯 JSON 产生正式 review 记录；所有非合规样例安全暂停且不得批准。 |

## 11. Git 隔离与并发

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| GIT-01 | 每个实施任务必须使用独立分支或 Git worktree，且实施模型只能修改任务允许的文件。 | 越界写入被阻止或使任务失败；任务有隔离工作区记录。 |
| GIT-02 | 主分支只有在自测、审核和复审通过后才能整合；冲突不得自动覆盖。 | 未过门禁无法整合；冲突转为人工处理状态。 |
| GIT-03 | 修改范围不重叠且无依赖的任务可以并行；修改同一文件、接口或有依赖的任务必须串行。 | 调度器能拒绝冲突并发。 |
| GIT-04 | 本地并发必须受 LM Studio 已加载模型和硬件能力限制；最大并发由用户或项目策略控制。 | 实际并发不超过策略和资源限制。 |
| GIT-05 | 文件边界应由工具权限或 OS 沙箱事前限制，并必须由 Git 差异事后核验；任一层发现越界都必须阻断整合。 | 越界操作不能无证据地进入主分支，即使事前限制失效也会被差异门禁捕获。 |
| GIT-06 | 未跟踪的计划内新文件必须进入 changed-files 范围核验、Reviewer diff 和 expected-output 存在性检查。`git diff --check` 的证据不得被扩大表述为覆盖所有未跟踪内容；如需检查其空白错误，必须附加明确的确定性检查。 | 未跟踪输出的路径和内容在范围与 Review Packet 测试中可见；缺失或含空白错误时确定性门禁失败。 |

## 12. 确定性控制平面与等待

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| CTRL-01 | 控制平面必须是普通程序而非 AI 模型，负责状态机、队列、模型进程/远程任务、预算、锁、检查点、事件日志、暂停恢复、重试和通知。 | 在无模型推理时仍能推进和查询确定性状态。 |
| CTRL-02 | 模型只应用于规划、判断、实施、审核、异常分析和整合。 | 状态查询、等待、预算比较等不会触发模型。 |
| CTRL-03 | 控制平面必须是可选边车，只在多模型、长时间或无人值守任务中启用。 | 普通人工工作流不依赖常驻控制平面。 |
| WAIT-01 | 顶层 Agent 不得高频调用模型轮询子任务。等待顺序必须为事件通知、非 LLM 状态检查、最后才是基于历史估时的指数退避轮询。 | 运行日志显示等待机制及调用次数。 |
| WAIT-02 | 只应在完成、失败、需要授权、无进展或超时时唤醒顶层 Agent。 | 普通无变化状态不产生模型唤醒。 |
| WAIT-03 | 耗时估算必须优先使用本机和实际供应商历史；互联网吞吐只作冷启动参考。 | 估算记录标明数据来源。 |
| WAIT-04 | 每次运行必须记录输入/输出 Token、首 Token 延迟、实际生成速度、工具/测试耗时、总耗时和重试；状态无变化时只读取增量日志。 | 运行指标齐全，连续查询不重复注入完整日志。 |

## 13. 持久化、中断与人工介入

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| STATE-01 | 全部执行状态必须持久化；每个计划、任务、模型调用和尝试必须有唯一编号。 | 重启后能通过编号恢复关系与状态。 |
| STATE-02 | 生命周期至少要表达草拟、等待授权、已排队、执行中、自测、等待审核、修改中、等待复审、已批准、等待输入、需要授权、降级运行、失败、已取消和已超时。 | 每种语义都有确定状态或由正交状态字段无歧义表达。 |
| STATE-03 | 恢复时必须先检查原任务是否仍运行，不得重复已完成任务或已完成收费调用，并从最近检查点继续且继续遵守原授权和预算。 | 进程重启测试无重复副作用或重复收费调用。 |
| STATE-04 | 追加事件与当前状态投影必须保存在同一个 SQLite 数据库，并在同一事务中提交；独立 JSONL 只能由已提交事件再生成，不得成为第二权威写入源。 | 在事件追加和状态更新之间模拟故障时，两者全部提交或全部回滚。 |
| STATE-05 | 每次模型调用必须可追溯到 run、task、attempt、call 与幂等 request key，并记录角色、provider、模型 ID/版本/family、本地/远程、provider 请求或会话 ID、Token、费用可用性、起止时间、耗时、终态和测试替身标志。 | 任一调用可通过数据库关联还原全部字段；`UNKNOWN` 在人工 resolve-call 前不能被 resume 或重复派发。 |
| HUMAN-01 | 人工介入必须支持只观察、安全暂停和立即冻结。 | 三种操作有不同且可观察的行为。 |
| HUMAN-02 | 安全暂停必须停止新派发、冻结未启动任务、让当前最小工作单元收尾、保存差异/测试/日志/费用/审核状态、释放写锁并生成人工接管摘要。 | 到达暂停状态后逐项证据完整。 |
| HUMAN-03 | 暂停生命周期至少要表达 `RUNNING`、`PAUSE_REQUESTED`、`QUIESCING`、`PAUSED`、`USER_TAKEOVER` 和 `RESUMING`。 | 状态迁移可查询且非法迁移被拒绝。 |
| HUMAN-04 | 立即冻结必须保留已有文件和日志，同时明确正在生成的模型任务可能无法从原 Token 位置续传。 | 冻结后现有证据存在，未声称支持 Token 级恢复。 |
| HUMAN-05 | 人工修改后恢复必须比较 Git 差异和文件哈希，只失效受影响的任务、测试和审核，展示调整后的剩余计划，并按原授权模式继续或请求增量授权。 | 未受影响的有效结果不会被无故重做。 |
| HUMAN-06 | 安全暂停的最小不可中断单元必须是一次外部进程或模型请求；返回后必须在下一次工具或模型调用前保存检查点。暂停超时后必须由用户选择继续等待或立即冻结，不得自动冻结。 | 暂停测试不会跨过下一个调用边界，超时也不会擅自终止当前请求。 |

## 14. Terminal 与存储分层

第一版 Terminal 命令名称确定为 `agentflow`，预期用户能力包括：

```text
agentflow plan show
agentflow plan authorize --hash <sha256>
agentflow start <plan-id>
agentflow status <run-id>
agentflow status <run-id> --watch
agentflow pause <run-id>
agentflow pause <run-id> --immediate
agentflow takeover <run-id>
agentflow handoff <run-id>
agentflow resolve-call <run-id> <call-id>
agentflow resume <run-id>
agentflow logs <run-id> --follow
agentflow cost <run-id>
agentflow cancel <run-id>
```

| 编号 | 要求 | 可验收结果 |
| --- | --- | --- |
| CLI-01 | 第一版必须能从 Terminal 启动计划并查看状态、日志和费用，且提供暂停、立即冻结、接管、恢复和取消操作。 | 上述用户能力均可通过稳定命令完成；最终语法可在确认后调整。 |
| CLI-02 | `status --watch` 只能读取本地状态，不能调用模型。 | 长时间观察期间模型调用计数不增加。 |
| CLI-03 | 第一版不要求开机自动服务；电脑重启后允许人工触发恢复。macOS 通知在核心闭环后作为非验收增强，且只用于完成、失败、需要授权和暂停超时。 | 无自启动或系统通知仍能通过 MVP；通知不会用于普通无变化状态。 |
| STORE-01 | 用户级存储必须保存模型注册表、跨项目脱敏表现、费用偏好、本地服务地址和用户信任等级。 | 用户配置可被多个项目复用且不含项目原文。 |
| STORE-02 | 项目级存储必须保存风险规则、隐私定义、允许模型、预算、分支策略和审核要求。 | 项目策略随项目隔离并可审计。 |
| STORE-03 | 单次运行必须保存计划、授权哈希、模型调用、状态变化、测试、审核、费用和最终结论。 | 任一运行可完整追溯。 |
| STORE-04 | 项目仓库只应跟踪 `.agentflow/project.toml` 等非敏感策略；运行记录、调用内容和敏感数据默认不得进入 Git。用户级配置和数据路径必须遵循平台惯例并允许环境变量覆盖。 | 新项目的默认忽略规则排除运行与敏感数据，且改变用户数据根目录不需要修改代码。 |

## 15. MVP 约束入口

第一版只承诺一个计划、三至四个串行任务、本地模型优先、Terminal 状态控制、SQLite 与追加式事件日志、独立 worktree、自测与只读审核、安全暂停、人工接管、中断恢复、事件驱动唤醒以及最小费用/调用记录。完整切片、非目标和验收矩阵以 [mvp.md](mvp.md) 为准。
